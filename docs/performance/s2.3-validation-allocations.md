# S2.3: allocation-free validation of clean data

Measured 2026-11-15 after S2.3, same machine and payloads as the [baseline](baseline.md),
[S2.1](s2.1-admission.md) and [S2.2](s2.2-pooled-buffers.md).

## What changed
- Validating a clean record, resource or scope allocates nothing (guarded by `AllocationTests`):
  issue lists created only on the first issue; pairwise key comparison for sets of ≤ 16 keys
  (no HashSet); indexed loops (no RepeatedField enumerators); location and nested-path strings
  built only when there is something to report.
- Load test: gRPC over 4 and 8 HTTP/2 connections added; GC experiment now opt-in
  (`GC_EXPERIMENT=1`).

## Micro-benchmarks: core handler (validate + respond)

| records | time: before → after | allocated: before → after |
|---|---|---|
| 512  | 94.1 µs → **25.6 µs** (3.7× faster) | 499 KB → **392 B** |
| 8192 | 1,440 µs → **412 µs** (3.5× faster) | 7.76 MB → **393 B** |

Validation now costs a fixed ~390 bytes per export (outcome + response), whatever the batch
size. Decoding is unchanged (~1 MB per 512 records, ~16 MB per 8192): it is now the main
allocation left on every path.

## Findings

- **S2.3 on gRPC: +5 to +13% throughput, a third less allocated, GC time halved** (c32: 4.2% →
  1.9%). On 8192-record batches: −31% allocated (23.4 → 16.2 MB per export), +5% throughput.
- **One HTTP/2 connection is the real gRPC ceiling**: ~5,200 exports/s ≈ 1.3 GB/s on one
  connection, the same at c32, c64 and c128. With 4 connections: **8,062 exports/s (+54%)**;
  with 8192-record batches **498/s = 4.1 M records/s (+70%)**. 8 connections add nothing
  over 4 on this machine (CPU-bound). Kestrel reads each HTTP/2 connection's frames one at a
  time, and that loop is the bottleneck; HTTP/1.1 runs used up to 32 connections, which is why
  HTTP looked faster than gRPC.
  - Kubernetes implication: many node agents (one connection each) spread naturally. A single
    gateway Collector on one connection tops out at ~1.3 GB/s per server pod; to go beyond it,
    it needs several connections, e.g. to several pods (headless Service + round-robin), which
    is the same mechanism as load balancing (S3).
- **8192-record batches still peak at ~2.2 GB RSS.** The GC heap holds ~1.8 GB while only ~8 ×
  16 MB of it can be live: with no memory limit on this Mac, Server GC lets garbage build up
  before collecting (gen-2 GCs: 0; GC time: 7%). Under a container memory limit the GC sizes its
  budgets from the limit; that is the next thing to measure (S3), rather than assume.
- Decoding is now the main allocation on every path (~2× the wire size for protobuf, ~15× for
  JSON). Reducing it would mean a custom parser or string interning: not planned.
