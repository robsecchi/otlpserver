# S2.4: logging at high request rates

Measured 2026-11-15: 5 s of gRPC exports (batch 512, concurrency 32) against a Release build,
counting the server's log entries (startup lines included).

| run | exports in 5 s | log entries: before S2.4 → after |
|---|---|---|
| default mode (no authentication) | ~16,000 | 30,106 → **12** |
| API keys, valid key | ~15,000 | (≈ 2 per export) → **10** |
| API keys, wrong key (24,098 refused) | 0 OK | (1+ per request) → **12**: one immediate warning + one 10-s summary |

## What was logged per request before
- `LogsExportHandler`: "Logs export processed" at Information, on every export.
- ASP.NET Core's authentication layer: every request runs the default authentication scheme,
  even with authentication off, and our handler reported "no header" as a FAILURE, which
  ASP.NET logs at Information (event 7). One line per request in every mode.
- Every partial success, full rejection, invalid key or token, STS outage, gzip bomb and
  rejected client certificate: one Warning each.

## Now
- The per-export line is Debug (metrics replace it in S3).
- With authentication off, the handler returns at once; a missing header is "no result", not a
  failure (the 401 still says "Missing Authorization header"). ASP.NET's per-attempt line for
  our handler is filtered to Warning: we report failures ourselves.
- Repeating warnings go through `AggregatedWarnings`: the first occurrence per (event, source)
  is logged immediately with its details, repeats are counted, and one summary per source is
  written every 10 s, e.g.
  `Rejected OTLP export: invalid API key (127.0.0.1): 24129 more time(s) in the last 10 s`.
  At most 1,000 sources per interval; the rest are grouped as "(other sources)".
- Data-quality warnings name the client (from the new `ExportContext`).
